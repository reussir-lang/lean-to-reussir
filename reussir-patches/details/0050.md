# Patch 0050: tagged opaque handles (one-word `Nat` and `Int`)

Patch file: `../0050-l2r-local-tagged-FFI-objects-an-odd-handle-is-an-imm.patch`
(made as commit `b4ea1ae1` in a scratch checkout, on top of 0017). Not a bug
fix: a small feature lean2rr needs to represent `Nat` and `Int` as one word.

## 1. Summary

An opaque Reussir record (`#[ffi(rust = "path")] pub struct T;`) is a
handle to a foreign, reference-counted box. Reussir copies such a handle by
incrementing the 32-bit count at offset 0 of the box, in line, and
releases it by calling a generated drop hook (the Rust type's `Drop`). The
patch adds an opt-in flag, `#[ffi(rust = "path", tagged)]`: a handle of
such a type may also be an odd word that is not a pointer at all, and
Reussir then increments the count, or calls the hook, only when the
handle's low bit is clear.

lean2rr declares `Nat` and `Int` this way. A small `Nat` `n` (below 2^63)
is the word `2n+1`, a small `Int` (the `int32` range) `lean_box` of its 32
bits; a big one is a pointer to a counted big number laid out as Lean's
`lean_mpz_object`. This is exactly Lean's own representation, and Lean's C
runtime makes the same low-bit test before every count update
(`lean_inc`, `lean_dec`).

## 2. Why lean2rr needs it

Before, `Nat` was a two-word `[value]` enum `{ Small(u64), Big(LBig) }`:
16 bytes in every record field (natively 8). A one-word encoding needs
someone to skip the reference counting of small values, and Reussir, not
lean2rr, inserts the counting (in records, closures, enums, its drop glue
and its acquire glue). Without the flag, Reussir would increment "the
count" of a small `Nat` at address `2n+1`: a crash. The alternatives are
weighed in the translation plan, §5.1 "One-word `Nat` and `Int`": a clone
hook is the same mechanism with a call per copy, and lean2rr cannot do the
counting itself because it cannot change the drop code Reussir generates.

## 3. Where in Reussir

- Frontend (Rust crates): `crates/reussir-core/src/semi/ctxt.rs` parses
  the attribute (`FfiSpec::Opaque(path, tagged)`) and records it on the
  record (`Record::ffi_tagged`). It travels through the textual HIR
  (`{ ffi tagged "path" }`, `semi/hir/{raw,build,print,grammar}`), the
  package interface copy (`semi/externs.rs`), monomorphization
  (`full/mono.rs`) into the MIR layout (`RecordLayout::Opaque { tagged }`,
  textual form `{ "path", @hook, tagged }`, `full/mir/*`), and codegen
  (`crates/reussir-codegen/src/lower/ty.rs`), which builds the dialect type
  through the C API (`reussirFFIObjectTypeGet(..., tagged)`, Rust bindings
  in `reussir-backend(-sys)`). The shared IR lexer gets a `tagged` keyword
  (also accepted as a name, so nothing called `tagged` stops parsing).
- Dialect: `include/Reussir/IR/ReussirTypes.td`, `FFIObjectType` gets a
  default-valued `bool` parameter, printed `!reussir.ffi_object<"path",
  @hook, tagged = true>` and omitted when false (existing IR is unchanged).
- Lowering: `lib/Conversion/BasicOpsLowering/BasicOpsLowering.cpp`, the
  only place where `rc.inc` and `rc.dec` of an `ffi_object` become code
  (`RcDecrementExpansion` leaves FFI objects to it). `beginRealBoxGuard`
  splits the block on `(ptrtoint p) & 1 == 0`; the increment (load, add,
  store, `assume(old >= 1)`) and the call to the cleanup hook go in the
  guarded block. Nothing is loaded from the handle before the test.

Two other places read the count of an arbitrary rc value, and skip
tagged objects with the patch: the optional `--instrument-nonlinear-ffi`
check (`lib/Conversion/InstrumentNonlinearFFI`, which reads the count of
FFI arguments before each import call), and the unique-carrying recursion
analysis (`isAssumableRcType` in
`lib/Transformation/UniqueCarryingRecursionAnalysis`, whose
`rc.assume_unique` reads a carried argument's count; it cannot fire for an
FFI object, which Reussir never creates fresh, but is excluded anyway).
Nothing else reads through an opaque handle: an `ffi_object` never
produces a reuse token (`ReussirRcDecOp::shouldProduceToken`), is not a
record, so the drop glue never defers it (patch 0014's
`isPlainSharedRecordBox`), and is never dereferenced by Reussir code. It
reaches foreign code only as its Rust type, which knows the encoding
(`leanrt::nat::LNat`'s `Drop` and `Clone` make the same test). Real boxes
are 8-aligned (at least 4: the count is a `u32` at offset 0), so the low
bit of a real handle is always clear, and an immediate (odd) is never
null.

## 4. Verification

An adversarial code review (lean2rr's prelude, runtime and lowering
changes, and this patch, with probe tests of every fast path at the
boundaries) found no problem in the feature; it pointed out the two count
reads above, now guarded.

- `tests/integration/conversion/tagged_ffi_object.mlir`: the type parses
  and prints; `rc.inc`/`rc.dec` of a tagged object lower to the guarded
  forms (checked line by line in the LLVM IR); an untagged object keeps
  the unguarded ones.
- `tests/integration/conversion/instrument_nonlinear_ffi_tagged.mlir`: the
  instrumentation skips a tagged argument and still checks an untagged one.
- `tests/integration/frontend/ffi_tagged.rr`: the attribute through HIR,
  MIR and MLIR.
- HIR and MIR round-trip unit tests; all 467 `reussir-core` unit tests
  pass. Existing FFI tests (`instrument_nonlinear_ffi.mlir`, `ffi_vec.rr`,
  `rc_delta.mlir`) pass unchanged.
- lean2rr: the runtime suite, the classic corpus, the Reussir benchmark
  suite, the round-7 big-number repros, and new tests of every `Nat`/`Int`
  operation at 2^62, 2^63 and 2^64 and of `Nat`s in every container,
  including a stress test that counts big-number allocations and frees
  (`tests/runtime/nat-alloc-check.sh`).

## 5. Effect on lean2rr

`Nat` and `Int` fields take 8 bytes instead of 16; small values are never
allocated; copying or dropping one is a bit test; `Array Nat` without the
`nat-arrays` pass is `RVec<Nat>` (one word per element) instead of an
array of boxes, and an `IO.Ref Nat` is a cell holding the handle. The
prelude's fast paths work on the words (plan §5.1).

## 6. Upstream note

The feature is general: any foreign type with a pointer-or-immediate
encoding (Lean objects, OCaml values, small-string optimizations) can use
it. A fuller version could let the foreign side choose the tag bit, or
lower the guard to a `select` where branches are costly.
